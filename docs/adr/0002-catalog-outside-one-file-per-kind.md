# ADR-0002: 台帳はツールの外に、1種類1ファイルで置く。分類はツールが決めない

- 状態: 採用
- 日付: 2026-11-25

## 背景

作者の環境の本番ログでは、件数の多い ERROR ほど誤検知だったという前例がある（1日500件を超える ERROR が、コードを読むと実害0件だった）。ログの文面だけで分類すると結論を誤る。分類はコードで裏を取る必要がある。

台帳は、複数の端末から書く。1本のファイルに追記すると、git のマージで毎回衝突する。

## 検討した案

1. ツールが文面のルールや LLM で分類する：裏取りが無いので、誤検知を実害と並べてしまう
2. 台帳をツールのリポジトリに置く：製品固有の知識（コードの場所・Issue・根拠）が、汎用の道具に混ざる
3. **台帳をツールの外（作業メモのリポジトリなど）に、1種類1ファイルの Markdown で置き、ツールは読むだけにする**

## 決定

3。

- 台帳のフォルダには、1種類1ファイルの Markdown と、取り込みの条件 `sources.json` を置く。`README.md` は台帳として読まない
- 1件は、フロントマターの `service`・`severity`・`component`・`message` で種類と突き合わせる。書いた条件はすべて満たす必要がある
- `message` は `/…/` で囲むと正規表現。似た種類を1件で束ねられる（例：フロントの nginx が遮断して返す 404 は、200 種類以上を1件にまとめる）
- 2件に当たるときは、完全一致の `message` を持つ方が勝つ。同じ強さならファイル名の順
- 台帳に当たらない種類は NEW として、1種類ずつ出す
- 書くのは人（または調査を手伝う AI エージェント）。ツールは15秒ごとにフォルダの更新時刻を見て、変わったら読み直す

## 理由

- 分類の正しさは、コードで裏を取る人が持つ。ツールは件数と傾向を出すことに専念する
- 1種類1ファイルなら、別の端末から別の種類を書いても衝突しない
- フロントマターは Obsidian のプロパティとしても読める

## 影響

- 初日は NEW が多い（2026-11-25 時点で約60種類）。台帳が育つと、NEW は「本当に新しい種類」だけになる
- フロントマターは台帳に要る形だけを読む簡易な読み方なので、YAML のほかの書き方（複数行の文字列など）は使えない
- 取り込みの条件（`sources.json`）を変えたら再起動が要る
