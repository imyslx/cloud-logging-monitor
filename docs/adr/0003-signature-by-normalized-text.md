# ADR-0003: 種類は「サービス・重要度・component・伏せた本文」で決める

- 状態: 採用
- 日付: 2026-11-25

## 背景

同じ原因のログでも、本文に batchId・URL・件数・時刻などが混ざるので、文字列のままでは毎回別物になる。逆に、本文が「Error occurred:」だけのログは、中身の違うエラーが1つにまとまってしまう。

FE の WARNING の多くは、本文の無いリクエストログ（Cloud Run が記録する 404）。

## 決定

種類の key は、次の4つを `sha1` にかけた先頭12文字。

1. サービス：`resource.labels.service_name`、無ければ `job_name`、無ければ `resource.type`
2. 重要度：`severity`
3. component：`jsonPayload.component`
4. 本文：
   - `jsonPayload.message` か `textPayload` の1行目を伏せたもの。伏せる順は URL → メールアドレス → UUID → 時刻 → 16進の長い列 → 英数字の長い ID → 数字（それぞれ `<url>`・`<email>`・`<uuid>`・`<time>`・`<hex>`・`<id>`・`<n>`）
   - エラーの名前と文面（`error_name`・`error_message`・`error`）があれば、伏せて「 — 」でつなぐ
   - 本文が無くリクエストのログなら `HTTP <ステータス> <メソッド> <パスの形>`。パスの形は、数字や ID（8桁以上の16進を含む）の段を `:id`、拡張子の付いたファイル名を `*.最後の拡張子`（ソースマップだけは `*.js.map` のように2つ）にして、6段まで見る
   - リクエストのログで、Referer が同じホストの画面のパス（ルート以外）なら、末尾に「（画面から）」を付ける。利用者の画面からの要求と、Referer を持たないスキャナーの要求を分けるため（例：デプロイのあとに古い画面が消えた部品を読みに行く 404 は利用者、`/assets/app.js` を探すのはスキャナー）
   - GCP の監査ログ（`protoPayload`）は、`methodName` と `status.message` から本文を作り、実行ごとに変わるリソース名を `<exec>` に伏せる
   - 本文の「」の中は `「<v>」` に伏せる（利用者が入れた名前などで種類が分かれないように）

## 理由

- 2026-11-25 の作者の環境の本番24時間分（2,017件）で 272 種類。うち 211 種類は FE への存在しないパスへの要求で、台帳の1件で束ねられた。残りは約60種類で、人が台帳で扱える
- エラーの名前と文面を添えると、同じ「failed」でも、トークン切れと権限不足が別の種類になる

## 影響

- 伏せ方を変えると key が変わる。台帳は key でなく条件で突き合わせているので（ADR-0002）、台帳は壊れない。手元の件数は別の種類として数え直しになる
- スキャナーのパスは種類が多い。束ねるのは台帳の正規表現の役目
- 「（画面から）」の判定は Referer に頼るので、Referer を送らない設定の利用者は、スキャナーの側に数えられる（2026-11-25 時点の作者の環境の本番では、利用者の要求には Referer が付いていた）
