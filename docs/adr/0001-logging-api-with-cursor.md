# ADR-0001: Logging API をカーソルで差分取り込みする（`gcloud logging read` を使わない）

- 状態: 採用
- 日付: 2026-11-25

## 背景

作者の環境では、対象のサービスの WARNING 以上が1日 2,000 件前後、ピークの1時間に約 1,000 件出る（2026-11-25 実測）。1つの処理だけで1分に数千件のログを出すものもある。

`gcloud logging read` は最新から降順に返し、`--limit` に達すると指定期間の古い側が丸ごと欠ける。1日分を1回で取ると 5,000 件の上限にほぼ届く。

GCP 側で数える手段は無い。Log Analytics は無効で、ログベースの指標も0本（2026-11-25 確認）。

## 検討した案

1. `gcloud logging read` を5分ごとに叩く：上限で古い側が欠ける。出力の JSON の扱いも重い
2. Log Analytics を有効にして SQL で数える：対象のプロジェクトの設定を変えることになる。チームの合意が要る
3. ログをシンクで BigQuery に流す：同上。費用も増える
4. **Logging API の `entries:list` を、古い順・ページ送りで、前回の続きから読む**

## 決定

4。gcloud はアクセストークンを取るためだけに使う（`gcloud auth print-access-token --configuration <構成名>`）。

- 範囲は「カーソル 〜 今−2分」。`timestamp>=カーソル` で引き直し、カーソルと同じ時刻のうち読んだ `insertId` は飛ばす
- 1回に読むのは、新しいログの入ったページで 20 枚（2万件）まで。読み切れなければ、最後に読んだ時刻でカーソルを止め、間を置かずに続きを読む
- 読み切れたら、カーソルを範囲の終わり（今−2分）まで進める
- 初回は7日さかのぼる
- 量が桁違いのログは、取り込みの条件（`sources.json` の `filter`）で除く

## 理由

- 古い順のページ送りなら件数の上限が無く、欠けない
- 対象のプロジェクトの設定を何も変えない。読むだけ
- Logging API の読み取りは課金されない（取り込み量で課金される）。5分ごとに数回の呼び出しなら、クォータ（1分60回）にも遠い

## 影響

- 書き込みが2分より遅れて届いたログは数えない
- 止めていた間の分は、保持期間（30日）のうちなら次の起動で取り戻す。それより長く止めると、その間は欠ける
- 取り込みの条件で除いたログは、このツールでは見えない。必要なら別に測る
